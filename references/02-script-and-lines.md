# 阶段 2：口播稿与拆句

## 2.1 写稿原则

- **同结构、换表达**：模式 A 下参考片的叙事骨架（Hook → 章节递进 → 回扣结尾）可以沿用，每句话必须自己写；**模式 B（只给主题）没有可沿用的原片骨架，改为从主题自建并列骨架**（`11-topic-only.md` §3）
- **开篇 15 秒定生死**：按「冲击 → 误区 → 拆穿 → 预告」四拍写 Hook（前 3 秒不许放 logo、自我介绍、背景介绍），开场至少写 4~6 句供快切使用；画面节奏与特效规范见 `10-first-15s.md`
- **每章只扛一个核心观点**：章内用「第一/第二/第三」或「四个格子」做并列结构——并列结构是后面总览页复用的基础（见 `04-shot-design.md`）
- **结尾必须回扣开篇**：把 Hook 里的矛盾在最后一句解决掉，别用「点赞关注」式的软结尾
- 字数预算：**TTS 约 240 字/分钟**；真人快语速 300~340 字/分钟。6 分钟的片子 TTS 稿写 1400 字左右

写作时同步用【画面：…】标注每段的画面意图，标注后面会被丢弃，但能逼自己检查「这段话有没有画面可做」——纯议论段落是动画的天敌。

## 2.2 拆句规则（决定字幕体验）

口播稿定稿后拆成字幕行，写入 `data/scenes.json`：

| 规则 | 数值 | 理由 |
|---|---|---|
| 每行字数 | **12~25 字** | 一屏读完不累；超长行会掉到第二行，拆句而不是缩字号 |
| 拆分点 | 句号/分号/逗号处，优先语义完整 | 半句话切屏观感极差 |
| 并列句 | 每条一行 | 后面镜头表靠行索引定位观点页 |
| 标点 | 行尾保留标点 | 字幕逐字进场按标点停顿 |

**行数即后续一切的地基**：镜头表的 `from`、对轴脚本的匹配、字幕切换点全部引用行索引。行拆错了后面全部错位，所以拆完先自读一遍：每行单独拎出来是否是一句完整的话。

## 2.3 scenes.json 结构

```json
{
  "fps": 30, "width": 1920, "height": 1080,
  "chapters": [
    { "id": 0, "title": "开场",     "tag": null },
    { "id": 1, "title": "先讲结论", "tag": "第 1 章" }
  ],
  "lines": [
    { "c": 0, "t": "第一行台词……" },
    { "c": 1, "t": "第二行台词……" }
  ]
}
```

- `c` = 章节 id；章节顺序必须连续递增
- `tag` 为 null 的章（开场/结尾）不显示左上角章节标签
- 章节 id 与场景组件数组一一对应（`Video.tsx` 里 `SCENE_COMPONENTS[chIdx]`）

## 2.4 派生文件

拆完顺手导出两个纯文本（用户经常要）：

- `analysis/口播稿-纯文本.md`：全部行拼起来，无任何标注 → 提词器/自己录音用
- 改稿后用同样规则重拆；**行索引变化时，镜头表和对轴脚本里的行号必须同步改**（这是最容易漏的）

## 2.5 交付口播稿并触发 G1（阻塞门）

三份文件（`口播稿-V1.md`、`口播稿-纯文本.md`、`scenes.json`）定稿后，**先把稿子交给用户，再用一次结构化二选一提问**，然后停在阶段 2 末尾等答复。完整协议见 `09-interaction-gates.md`。

- **交付**：口播稿 + 提词器纯文本 + `data/scenes.json`（报出共 N 句 / 约 X 字 / 预计时长）
- **一次问完**：「自己拿着稿子录」还是「让 AI 直接生成配音」；稿子要改也在同一轮说完，改完重新交付，**不额外再开一次选择**
- **主动说明字数预算冲突**：G1 发生在选配音之前，本稿按 TTS 约 240 字/分钟估算；若用户选真人录音（实测语速快约 30%），成片会短 20~25%，想维持时长可现在略扩写。别等成片交付时才被发现
- **未拿到明确选择前**：不生成任何音频、不建 `timeline.json`、不搭画面、不写镜头表

> 必须先拆句定稿再问 G1——行数决定后续一切（镜头表 `from`、对轴、字幕切换点全引用行索引）。用户在 G1 里改稿导致行数变化，镜头表和对轴脚本的行号要同步重排。
