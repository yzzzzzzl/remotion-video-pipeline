# 两道用户确认门（G1 / G2）

> **这是流程硬规则，不是建议。** 本流水线以前是「一口气从阶段 0 跑到渲染完」；但口播稿和配音是整条链路里返工成本最高的两处——改一句台词要同时动音轨、`timeline.json`、镜头表 `from`、画面文案四处（见 `06-qc-render.md` §删句三同步）。所以必须在成本还很低的时候停下来问人。

## 全局原则：只打断两次

| 门 | 卡在哪 | 问什么 | 是否阻塞 |
|---|---|---|---|
| **G1 选配音** | 阶段 2 完成（口播稿 + 拆句定稿）→ 阶段 3 之前 | 自己录 / AI 生成 | **阻塞** |
| **G2 审听** | 阶段 3 完成（`voiceover.mp3` + `timeline.json`）→ 阶段 4 之前 | 音频没问题吗 | **阻塞**（AI 配音强制） |

- 阶段 1 的配方卡确认（`01-reference-teardown.md` §1.5 / `11-topic-only.md` §6）是**软门**：给用户看一眼「骨架理解对了没」，不停机等回复。
- 除 G1 / G2 外**不要反复追问**音色、语速、精确时长、字体、配色、每页动画……除非用户主动提。用户要的是「问一次就往下走」，不是被问十次。
- v1.3.0 的开头 15 秒规范（`10-first-15s.md`）是**画面规范，不是第三道门**：画风、切几页、用哪些特效按阶段 1 配方卡自行决定，不因此再问用户一次。
- v1.4.0 的「只给主题」模式（`11-topic-only.md`）**同样不是第三道门**：画幅 / 时长 / 配色等规格用默认值兜底，不追问用户；只有用户主动提才覆盖。
- 两道门都遵守：**沉默 ≠ 默认通过**。没拿到明确答复就停在原地，不猜、不替用户决定、不"先做出来再说"。

宿主工具映射（本环境）：结构化二选一用 `AskUserQuestion`；交付口播稿 / 音频用 `present_files`（或直接给绝对路径让用户本地打开）。换宿主时保持语义即可。

---

## G1：交付口播稿 + 配音方式二选一

**触发条件**：`analysis/口播稿-V1.md`、`analysis/口播稿-纯文本.md`、`data/scenes.json` 三份都定稿（拆句行数定下来，后面才有得对齐）。

**先把稿子交付给用户看，再用一次结构化二选一提问。** 提问模板可直接用：

> 口播稿写好了（附路径：共 N 句 / 约 X 字，按 TTS 估算约 M 分 S 秒）。进配音前你选一种：
> - **A 我自己拿着稿子录** —— 我把提词器纯文本给你，录完把音频放进 `source/`，可以分几段录，我来做逐字对轴。
> - **B 让 AI 直接生成** —— 我用 edge-tts 逐句配音，生成后**先给你试听，你确认没问题我再做画面和成片**。
>
> 稿子要是想改，也在这一轮一起说。

### 这一门的硬要求

1. **只问一次**。绝不拆成「先看稿子确认吗？」+「配音选哪个？」两轮。
2. **同一轮吸收改稿意见**：用户说「某段删掉 / 改写 / 太长了」→ 改稿、重拆行、重新交付，配音方式仍在这一轮定下来；改完不要额外再开一次选择。行数变了要同步提醒自己：`04` 镜头表的 `from` 全部按新行索引重排。
3. **字数预算的先天冲突要主动说明**：G1 发生在选配音之前，写稿只能按默认口径（TTS 约 240 字/分钟）。提问里必须补一句：若选 A 真人录音（实测语速快约 30%），成片会短约 20~25%；想维持时长可现在略扩写。否则用户拿到成片才发现变短。
4. **G1 之前不预选路线**：不生成任何音频、不建 `timeline.json`、不搭画面、不写镜头表；也别先替用户装某条路线的 Python 包（体检用 `check_env.py` 默认 `both` 全查即可）。
5. **阻塞**：没拿到明确选择前停在阶段 2 末尾。

### 分叉后的动作

- **选 A（自己录）**：交付 `analysis/口播稿-纯文本.md`（提词器格式、无标注），明确告知文件放 `source/`，支持分段录音（处理方式见 `03-audio-timeline.md` §分段录音）。然后**等文件**，期间不生成 TTS、不催第二次。
- **选 B（AI 生成）**：进阶段 3 路线 A；生成完毕后**必须**走 G2，不得直接进阶段 4。

## G2：音频试听确认（做成片前最后一道）

**触发**：`public/voiceover.mp3` + `data/timeline.json` 生成完毕、阶段 4 之前。
**只要配音是 AI 生成的，这道门强制生效**；真人录音路线同样建议过一遍——分段剪点和垫静音最容易听出不自然，而这时候改还来得及。

### 执行步骤

1. **把音轨真正交给用户听**：用 `present_files` 呈现 `voiceover.mp3`（或给出绝对路径让用户本地播放），不要只在终端打印一句「音频已生成，时长 3:52」。
2. 附一张**试听自检卡**，让用户不用逐句猜哪里要留意：

   ```
   音轨：<绝对路径>   时长 M:SS   句数 N   音色 zh-CN-YunxiNeural   语速 +12%
   逐句对照：analysis/口播稿-纯文本.md（第 1..N 句 == 音频顺序）
   留意点：章节间 0.9s 静音 / 开头 0.4s / 结尾 1.6s / 有无多音字读错、断句别扭
   （真人路线另附：对齐匹配率 __%，低于 85% 不要放行）
   ```

3. **明确问一句**：「配音听起来没问题吗？确认后我才开始做画面和成片。」
4. **等明确确认**：`OK / 可以 / 没问题 / 就这样 / 继续` 算通过；沉默、答非所问、「你看着办」「你决定」不算，保持等待，必要时用一句最短的话再确认一次，绝不顺势往下跑。

### 用户不满意时怎么改

改完**重新交付试听**，直到拿到明确确认（这属于同一道门内的迭代，不违反「只打断两次」）：

| 反馈 | 动作 |
|---|---|
| 某个字/词读错、多音字 | 改 `scenes.json` 该行文本或换同音词/加注音，只重跑该句 TTS 再拼接 |
| 整体太快 / 太慢 | 改 `--rate` 重跑 `make_audio.py`，`timeline.json` 整体重算——画面还没做，零返工成本 |
| 某句停顿别扭、断句错 | 调行间/章节静音，或重新拆行；**行数变了必须同步 `04` 镜头表 `from`** |
| 音色不喜欢 | 换 `--voice`（Yunxi / Yunjian / Xiaoxiao）整段重跑 |
| 想改成自己录 | 直接回到 G1 的分叉 A，不需要用户重新做一次选择，说明一句即可 |

### 阻塞线

G2 通过之前：**禁止**进入阶段 4 / 5 / 6，禁止写镜头表动画、禁止 `remotion render` 出 MP4。
理由很实际：全片渲染约 6× 实时（4 分钟片子渲 25 分钟），此刻改音频是几分钟的事，一进画面就变成「音轨 + timeline + 镜头表 + 画面文案」四处同步的返工。

---

## 改稿阶段（阶段 7）怎么算门

| 改动 | 是否重走门 |
|---|---|
| 换配音、重录、增删句、调节奏 → **音轨变了** | **重走 G2**，把新音轨再交付一次 |
| 只动画面（配色、某页动画、画面文案），音轨不变 | 不用重走，改完直接渲染 |
| 口播稿整篇重写 | 视同新项目，**回到 G1** |

---

## 反模式（这次改动要根治的）

- ❌ 阶段 0 就把「配音方式」定死，一路跑到渲染完才把成片给用户。
- ❌ 口播稿写完不问，直接默认走 TTS。
- ❌ TTS 生成完不交付试听，默默开始搭工程、渲染 MP4。
- ❌ 用「我默认你觉得没问题」「先渲出来你再看」跳过 G2。
- ❌ 反向过度：每做一步都问「要不要继续」，把「确认一次」变成「打断十次」。
- ❌ G1 还没问就先装好某条路线的依赖，或在提问前替用户选好音色/语速。
